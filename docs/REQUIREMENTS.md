# FB 社團拍賣監控 — 需求

## 0. 一句話

從「錯過拍賣文」的通知工具，長成「私密社團拍賣資料的個人資料庫 + 分析介面」。

通知只是第一個出海口，不是系統的目的。這個認知改變了資料層該怎麼設計。

## 1. 需求清單

| # | 需求 | 階段 | 狀態 |
|---|---|---|---|
| R1 | 新 listing 出現後數分鐘內收到推播 | 現在 | 已確認 |
| R2 | 查詢歷史貼文 | 之後 | 新增 |
| R3 | 比價（同類品項的價格分布、行情） | 之後 | 新增 |
| R4 | 問答式分析：提問 → 撈資料 → LLM 分析 → 回 Discord | 之後 | 已釐清 |
| R5 | 圖片保存與查找 | 之後 | 新增 |
| R6 | Discord 作為主要互動介面 | 之後 | 已升級 |

## 2. 最重要的一件事

**擴充性的成本幾乎全在資料採集與保存，不在程式架構。**

程式架構寫錯可以重構，兩天的事。沒採集下來的資料永遠補不回來——貼文會被刪、圖片連結會過期、賣家會退社團。R2 到 R5 全部依賴「當時有沒有存下來」。

所以現在唯一真正要做對的是**採什麼、存什麼**。其餘都可以延後。

## 3. 三個不可逆決定

這三件事必須從 Stage 1 就做對，事後無法補救。

### 3.1 保存原始 DOM snapshot

每次抓取把原始 DOM 壓縮存檔，不是只存解析後的欄位。

理由有二：
- FB 改版一定會打壞解析器。存了 raw 就能回溯重新解析，不用接受一段資料斷層。
- R3／R5 之後會需要現在沒想到的欄位。有 raw 就能回填，沒有就永遠缺。

### 3.2 圖片必須立刻下載落地

FB 的 CDN 圖片網址帶簽章、會過期，幾天到幾週後就失效。

**只存 URL 等於沒存。** R5 要做圖片分析，圖片必須在抓到的當下就下載到本機。

附帶好處：下載走的是 CDN 而非 FB 主站，風險低很多。

### 3.3 完整欄位，不做有損擷取

原 spec 寫「標題取前 120 字」，那是為通知推播設計的。對 R2／R3 來說是有損壓縮。

要存的最小集合：全文、價格、賣家識別、貼文時間、抓取時間、社團、所有圖片、permalink。賣家識別和時間戳事後完全無法回填，比價與信譽分析全靠它們。

## 4. 需求反推出來的張力

### 4.1 R2 與風險限制直接衝突

「查詢舊貼文」意味著歷史回填，回填意味著深度分頁——而深度分頁是風險排序裡僅次於機房 IP 的高風險動作，原本的限制明確禁止它。

**解法：把歷史回填和常態輪詢徹底分開。**

| | 常態輪詢 | 歷史回填 |
|---|---|---|
| 觸發 | daemon 自動 | 人工，一次性 |
| 範圍 | 時間序第一屏 | 深度分頁 |
| 速度 | 90–240 秒一次 | 極慢，可跑數天 |
| 帳號 | 備用帳號 | 備用帳號 |

回填邏輯不放進 daemon。否則某天改壞了，它會在背景瘋狂分頁直到帳號被鎖。

另外要接受一個事實：**歷史深度有上限。** 社團動態往回捲會愈來愈慢且不可靠，實際能回填多少要 Stage 1 之後才知道。比較務實的期待是「從系統上線那天開始累積」，回填當作額外收穫。

### 4.2 R4 不是 MCP

原先誤判成 MCP。釐清後的實際流程是：

```
Discord 提問
  → 後端解析問題，從 store 撈出相關 listing
  → 組 prompt 送給 LLM
  → 取回應
  → 發回 Discord
```

**LLM 是被後端呼叫的服務，不是來拉資料的 client。** 方向跟 MCP 相反。

這是好消息：公開 HTTPS 端點、OAuth、方案限制那一整組門檻全部消失。不需要把任何東西暴露到公網。

#### LLM 管道的選擇

目標是用既有 ChatGPT 訂閱、不另外付 API 費。三條路：

| 方式 | 費用 | 穩定性 | 風險 |
|---|---|---|---|
| Codex CLI (`codex exec`) | 訂閱內 | 官方支援 | 低 |
| OpenAI API | 按量計費 | 最穩 | 無 |
| 反向工程 web client | 免費 | 半衰期數月 | 帳號可能被停 |

**選 Codex CLI。** 它支援用 ChatGPT Plus/Pro 訂閱登入，並提供 `codex exec` 非互動模式供腳本驅動——正是「用訂閱不付 API 費」要的東西，而且是官方管道。

反向工程 client 不建議：acheong08/ChatGPT 曾是最大的一個，已被 DMCA 下架。更關鍵的是跑它可能害 ChatGPT 帳號被停，而那個帳號的訂閱正是要利用的東西。

已知限制：
- Codex 是程式導向的 agent，做一般性價格分析會有點阻抗不匹配，但可行
- ChatGPT 方案的登入需要瀏覽器點一次 OAuth，headless 環境麻煩。但本專案為了 FB 登入本來就要跑 Xvfb + VNC，同一套基礎設施可以共用
- 也支援 device code flow 與 `--with-access-token` 做無瀏覽器登入

**架構上必須把 LLM 抽象成介面**，實作可替換。這是最該放擴充點的地方——三條路各有壽命，換實作不該波及其他層。

在真的接上去之前，先量一次實際的 token 量再決定要不要走訂閱路線。若用量比想像小，直接用 API 可能反而單純。

### 4.3 R6 升級成主要介面

R4 釐清後，Discord 不再只是輸出管道，而是**使用者提問的入口**。

| 形式 | 用途 | 需求階段 |
|---|---|---|
| Webhook | 單向推播新 listing 通知 | R1，極低成本 |
| Bot + slash command | 提問、查詢、比價 | R4，必要 |

通知仍走 webhook（一個 HTTP POST 就夠）。問答流程需要 bot 常駐連線與指令處理，那是 R4 的一部分，不是可選項。

## 5. 分層邊界

這個現在定很便宜，之後改很貴。

```
collector  ──寫入──>  store  <──讀取──  notifier ──> Discord webhook
(爬蟲)                (唯一真實來源)
                          ^
backfill   ──寫入──>      │
(人工觸發)                │
                          │
                      Discord bot ──> retriever ──> llm.Provider
                      (提問入口)      (撈相關資料)   ├─ Codex CLI
                                                     ├─ OpenAI API
                                                     └─ (其他)
```

兩條規則：

1. **collector 只負責取得並寫入原始資料**，不做通知、不做分析、不做判斷。其他所有東西都是 store 的讀者。爬蟲是最脆弱、最不該頻繁改動的部分，加功能不該波及它。
2. **LLM 藏在 `llm.Provider` 介面後面。** 三條管道壽命各異，換實作只該動一個檔案。

## 6. 資料模型草案

```
snapshots    抓取原始記錄：id, group_id, fetched_at, raw_dom(壓縮), parser_version
listings     id(PK), group_id, seller_id, title, body, price, currency,
             posted_at, first_seen, last_seen, permalink, status, parser_version
price_history listing_id, price, observed_at        -- 賣家改價
images       listing_id, cdn_url, local_path, sha256, downloaded_at
sellers      id, display_name, first_seen
notifications listing_id, channel, sent_at
```

幾個設計理由：
- `parser_version` 讓解析器改版後能辨識哪些資料該用新版重跑，不必全量重解析
- `price_history` 獨立成表，因為改價本身是比價的訊號
- `images.sha256` 用來跨 listing 找重複圖片——同一賣家重發、或盜圖轉賣，都靠這個抓

## 7. 現在不要做的事

避免為了「擴充性」而過度設計：

- 不要 message queue。兩個社團的量，單一程序內的 channel 就夠。
- 不要微服務。一個 binary、多個模組。
- 不要寫 MCP server。R4 釐清後不需要它。
- 不要現在接 LLM。先把資料存對，沒有資料的分析是空的。
- 不要現在設計比價演算法。等有幾個月真實資料再說，否則是憑空想像。
- 不要現在換 Postgres。SQLite 開 WAL 足以應付，真的撞牆再換。

## 8. 待決定

- **歷史深度期望**：只從上線起累積可以接受嗎？還是回填是硬需求？這決定 4.1 的回填模式要不要做。
- **語言與技術選型**：需求已大致定案，可以開始選了。已知張力見下。

### 8.1 選型張力

| 層 | Python 優勢 | Go 優勢 |
|---|---|---|
| collector（爬蟲） | Patchright／Camoufox 生態成熟 | 只有 go-rod |
| store / 排程 / daemon | — | 單一 binary、併發、部署簡單 |
| Discord bot | 兩邊都成熟 | 兩邊都成熟 |
| llm.Provider | — | 都是 subprocess 或 HTTP，無差異 |

唯一實質差距在 collector。兩個選項：

- **全 Go**：接受 go-rod。前面分析過，登入態下主要防線是 IP、節奏、profile 穩定性，JS 指紋不是決定性因素。
- **分層拆語言**：collector 用 Python，其餘用 Go，中間以 store 為界。代價是兩套執行環境的運維複雜度。

分層拆的邊界剛好落在 §5 已經畫好的那條線上，所以這個選擇可以延後到 collector 真的遇到偵測問題時再做，不會變成重寫。
