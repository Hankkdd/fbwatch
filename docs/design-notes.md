# 設計筆記

這份記的是「為什麼這樣做」，多半是實際壞掉之後的修正。安裝與操作看 [README](../README.md)。

數字是在一個台灣的二手買賣社團上量的，只能當量級參考 —— 換個社團多半不一樣，
但得出數字的方法可以照抄。貼文內容與賣家資訊都已移除。

## 圖片

商品照片存進 MinIO，以內容雜湊（sha256）為 key，中繼資料在 Postgres
的 `images` 與 `listing_images` 兩張表。拆兩張是因為多對多 ——
實測跨社團轉貼佔 39%，同一張圖會被多則 listing 引用，只該存一份。

用 MinIO 而非檔案系統，理由是管理性而非容量（估算約 20GB/年）：
content-addressed 的路徑用眼睛看不出是什麼，MinIO 的 console 可以
直接瀏覽與預覽。console 綁在 `BIND_IP` 上。

**圖片下載不需要登入態也不需要瀏覽器** —— 走 `scontent.*.fbcdn.net`，
純 HTTP GET 即可。所以這段對帳號風險幾乎為零：不同主機、不帶 session、
不增加 facebook.com 的請求。但網址帶簽章會過期，必須在抓到詳情頁的
當下就下載，不能只存網址。

兩種頁型的照片欄位不同，都要支援：

| 頁型 | 欄位 |
|---|---|
| 商品頁 | `listing_photos[].image` |
| 貼文頁 | `media.photo_image` 與 `all_subattachments.nodes[].media.image` |

只從這些已知欄位取，不是掃整份文件找 scontent 網址 —— 那會把大頭貼、
表情符號、介面圖示一起抓進來（實測誤抓過 80x80 的大頭貼），
另外再加尺寸下限 200px 把關。

已知限制：多圖貼文的初始 HTML 只帶一部分（實測 42 張的貼文拿到 9 張），
要全部得翻圖片檢視器，那是每張一次請求，不划算。

## 7-11 賣貨便

第二個來源，跟 FB 那條路完全分開。純 HTTP、不需登入、不需瀏覽器，
所以沒有 session、熔斷、帳號風險那一整套，它失敗也不影響 FB 的輪詢。
商品資料全在 `data-product` 屬性裡的一包 JSON，連精確上架時間都有。

追蹤清單在 `shops` 表（第一次由 `config/seed.yaml` 種進去），`label` 是自訂稱呼，
改 `enabled` 即時生效不必重啟。

### 庫存有三個數字，只有一個能用

```
Cgds_Inventory  賣家上架時填的數量 —— 有人下單時它動都不動
Cgds_Qty_Reg    已經被下單的
Inventory       還買得到的
```

一開始讀的是 `Cgds_Inventory`，結果完售偵測從上線到 2026-10-08 一次都沒觸發過。
當天實測：賣場 139 件裡有 42 件 `Inventory` 已經是 0，但 `Cgds_Inventory`
全都還是原值。合計庫存我們記 344，實際只剩 143。

升級時把既有的 `inventory` 全清成 NULL（migration 009），讓下一輪重新建立
正確基準 —— 不清的話改讀正確欄位會一次噴出 42 則完售通知洗版。
比對本來就會跳過沒有基準的商品，所以清掉等於安靜重建。

### 售價只能看還買得到的規格

一件商品常常同時掛著主體與配件。一件商品有完整盒裝 $2700 與小配件 $30 兩種規格，配件賣掉之後若還拿所有規格的最低價當售價，
通知會變成「新上架 $30」，跟實際買得到的價格差了快一百倍 ——
2026-10-08 真的這樣發出去過一次，當天 148 件裡有 11 件報的是賣完規格的價格。

`MinPrice()` 只看 `Remaining > 0` 的規格。整件賣完時沒有「買得到的價格」，
`Price()` 會退回 `LastPrice()`，讓完售與下架的通知還是有數字可寫。

### 「新上架」要跟「重新上架」分開

整件賣完的商品會被賣貨便從賣場頁藏起來，賣家補了貨又冒出來 ——
對輪詢來說就是一件沒看過的商品，於是報成新上架。
2026-10-08 的 23 則「新上架」裡有 16 則是這樣來的，點進去會發現商品
排在賣場第 108 位、建檔時間是七月，看起來像壞掉了。

分辨方法是比對 `Cgdd_Create_Datetime` 與 `shops.added_at`：建檔時間早於
我們開始追蹤的，就不是新上架，發 `relist`。這也是原本「一直在更新」
那個感覺的主要來源 —— 真正的新商品當天只有 7 件。

### 「賣掉」有兩種長相

| 長相 | 偵測方式 | 事件 |
|---|---|---|
| 剩餘量降到 0，商品還在頁面上 | 比對 `Inventory` | `soldout` |
| 商品從頁面上消失 | 本輪沒再出現 | `removed` |

第二種不一定是賣家刪掉的 —— 整件賣完也會被平台藏起來，之後補貨又會回來
（已經實際發生過一次，`removed_at` 被重新清掉）。所以 `removed` 的意思是
「現在買不到了」，不是「永遠消失了」。

第二種以前完全看不到，因為比對只跑在本輪抓到的商品上。
指名預訂品（商品名寫「某某專拍」那種）幾乎都走這條路，買家付完款賣家就下架。
2026-10-08 早上有 18 件這樣消失，拿名字去平台搜尋也是 0 筆，確認是真的移除。

移除偵測有一道防呆：一輪少掉四成以上就判定抓取不完整並報錯，不標記任何移除。
頁面只回傳一部分時，剩下的會看起來像被刪光。實測連抓三次都穩定是同一個數字，
而真實的批次刪除是 18/157（11%），所以門檻放得過真實批次、擋得住被截斷的頁面。

### 商品網址：平台沒有，但 HTML 錨點可以

賣貨便沒有商品頁。查過的死路：

- 搜尋是 `POST /CPF0102/QueryProducts`，帶 `__RequestVerificationToken` CSRF，
  沒有 GET 版（`?keyword=` 直接被忽略，整頁商品照樣回來）
- 商品彈窗 `POST /CPF0102/PopupProduct` 同樣是 POST
- `?pid=` / `?productId=` / `/general/product/<id>` 之類的路由都不存在（302 或被忽略）
- `sitemap.xml` 與 `robots.txt` 都只是轉址回首頁
- 平台自己的「複製網址」按鈕，JS 寫死 `return document.location.href` ——
  複製的就是賣場頁；旁邊的 FB／LINE 分享也一樣

**但不需要平台配合**：每張商品卡片的 `<a>` 都帶著 `id="<商品id>"`，
所以 `…/general/detail/<賣場>#<商品id>` 會讓瀏覽器自己捲到那件商品。
2026-10-08 用獨立的 headless Chrome 實測，頁高 47289px、開這個網址停在
44281px，目標商品正好在視窗頂端。頁面沒有 lazy load、也沒有會改寫 hash
或捲回頂端的 JS，所以位置穩定。商品被下架時片段找不到，退化成停在賣場頁
頂端，不會壞掉。

卡片同時帶商品圖補強：圖片有各自的網址而且公開可讀（不需 cookie，實測
HTTP 200），認商品靠圖比靠文字快。
還買得到的用大圖，已經賣掉或下架的用小圖 —— 後者只是「有人買走了」的動態，
不值得佔滿整個頻道。

卡片同時還是要給 `content`：手機推播顯示的是 `content`，
只有 embed 的訊息推播出來會是空的一條，等於白做。
商品 JSON 的 `Cgdd_Product_Status` 是**保存情況**不是上下架：`1` 新品、`2` 二手
（2026-11-09 對照彈窗確認）。有沒有貨看剩餘數量。二手商品的通知會在第一行標「（二手）」。

`content` 最後一行也放商品網址（用 `<>` 包住，不另外長預覽）：比價 bot 讀被回覆的訊息時
只看得到 `content`，看不到卡片，沒有這行它查不到是哪一件。

`content` 分兩行，稱呼與「發生什麼」在上、商品名稱獨佔一行：

```
賣場名稱　新上架 $2200
商品完整名稱
```

三段擠成一行時商品名稱夾在中間，手機寬度下會亂折行。

## 關鍵字提示

在意的主題命中時，通知最上面多一行提示詞。**原文一個字都不動**，判斷還是交給人，
那一行只是讓你在通知列上就先知道值不值得點開：

```
**[限量品出現了]**
**售 限量版海報 A款**
附特典，店到店 +60
<https://www.facebook.com/...>
...
```

粗體與方框都在輸出那一層加，不是存在 `line` 欄位裡 ——
改句子的人不用記得補，想換整體樣式也只要動一個地方。

清單在 `keywords` 表（第一次由 `config/seed.yaml` 種進去），改表即時生效。命中多個就每個各一行，依 `priority`
由小到大（稀有的先講）；實測 465 則裡有 17 則命中多個，最多三個。
整體 68 則會標記，佔 15%。

### 縮寫不能直接當子字串找

社團裡兩三個字母的簡稱很常見，但直接比對會炸。
拿 464 則歷史貼文實測，某個兩字母縮寫命中 16 則，其中 13 則是這些字裡剛好有那兩個字母：

以 `LE`（限量）為例，這些字裡剛好有這兩個字母：

| 誤判 | 來源 |
|---|---|
| `Sleeve` | 卡套 |
| `Bundle` | 套組 |
| `LED` | 燈條 |
| `Complete` | 完整盒組 |
| `Single` | 單曲 |
| `Alex` | 人名 |

商品名、品牌、人名都會中，而且每個社團中的字不一樣。

所以拉丁字母的樣式一律加 `\b`。Go 的 `\b` 是 ASCII 定義的，中文字算非字元 ——
「的LE版」兩側都成立、「Sleeve」兩側都不成立，剛好就是要的行為。
中文樣式則直接子字串，中文沒有詞界可用。

### 同義詞要從資料挖，不能憑印象列

人憑印象列的清單跟社團實際在用的講法差很多：

拿四個想追的東西，比對「憑印象列的詞」與「21 天語料裡實際的講法」：

| 想追的 | 憑印象列的詞 | 資料裡實際在用的 |
|---|---|---|
| A | 正式名稱 **2 則** | 英文原名 7、俗稱 6、縮寫 4 |
| B | 正式名稱 17 則 | 另有詞序顛倒的寫法 7 則 |
| C | 正式名稱 19 則 | 某個暱稱 25 則，**比正式名稱還多** |
| D | 正式名稱與常見簡稱 **各 0 則** | 只有另一個簡稱 3 則 |

D 那一列最值得記：憑印象列的兩個詞在 21 天語料裡一次都沒出現，
真正在用的是第三個講法。沒去挖資料的話，那個關鍵字等於沒開。

反過來也要排除「看起來像、實際不是」的詞 —— 挖的時候把命中的貼文逐則看過，
確認是不是真的在講那個東西。異體字（「汙／污」「裏／里」）只能靠列舉。

挖法：把歷史貼文倒出來，拿候選詞逐一數出現次數，再把命中的抽樣讀過：

```sql
SELECT count(*) FROM listings WHERE COALESCE(body, body_feed) ILIKE '%候選詞%';
```

靜音的賣家仍然只佔一行，但命中的標籤會補在後面 ——
不然在意的東西只因為賣家被靜音就整個漏掉。

## 給比價 bot 查貼文的 MCP 服務

外部比價 bot看到通知時只有 Discord 上的文字。很多貼文內文只寫
「售如標題」，照片也不在通知裡，它判斷不了。`cmd/mcp` 讓它拿通知裡的連結查回 fbwatch 存下來的資料。

| 工具 | 給什麼 | 回什麼 |
|---|---|---|
| `listing` | FB 貼文連結或 ID | 標題、標價（`nt_tag`）、內文、地區、賣家、最多 8 張照片（縮到長邊 1024） |
| `shop` | 賣貨便連結或 GM 代號，可帶 `#商品編號` | 即時商品清單；指定單件時附商品圖 |
| `market` | 品名關鍵字（中英文各一，最多 5 個） | 近 120 天社團貼文開價（跨社團轉貼合併、擷取關鍵字附近的內文）與賣貨便店家開價 |
| `fx` | 幣別，可帶金額 | 外幣兌台幣（ExchangeRate-API 市場中價，快取 6 小時；台灣銀行牌告頁會擋機器人） |

安全邊界：

- `listing` 只查本地資料庫，用唯讀角色 `fbwatch_mcp`（migration 014），不會連 FB
- `shop` 只連 `myship.7-11.com.tw`，模型給的只是代號，不是網址
- `market` 只查本地資料庫；關鍵字裡的 `%`、`_` 會跳脫，不然一個「%」就能把整張表倒出來
- `fx` 只連固定的匯率來源，模型只能選幣別
- 賣家寫的標題與內文會框在「只當資料看」的分隔線裡
- 不對主機開 port，只掛在指定的外部網路；另外要求 `FBWATCH_MCP_TOKEN`

設定：`.env` 加 `COMPOSE_PROFILES=mcp`、`FBWATCH_MCP_PG_PASSWORD`、`FBWATCH_MCP_TOKEN`。
collector 啟動時會用第二個替唯讀角色開登入。

這個服務擺在 compose profile 後面，**預設不啟動**。一開始是用 `${VAR:?}` 要求密鑰，
結果 compose 的 interpolation 是對整份檔案做的 —— 只想跑 collector 的人也會被擋下來，
連 `docker compose up collector` 都直接失敗。必填檢查因此搬進 `cmd/mcp`：
沒有 token 服務就拒絕啟動，而不是啟動後不驗證。

### 自動叫比價 bot

`keywords.summon = true` 的主題命中時，通知第一行尾巴會加上 `<@bot>`，bot 被 tag 就自動比價。
預設全關（`config/seed.yaml` 裡每個關鍵字自己設 `summon`）；之後要改：

```sql
UPDATE keywords SET summon = TRUE WHERE label = '預購';
```

不叫的情況：靜音賣家、徵求文（`status = wanted`）、賣貨便的完售／下架／漲價 —— 那些不是購買機會。
實測開三個關鍵字時一天大約命中 2 則（FB 1.4、賣貨便 0.6）。

所有 webhook 都明確帶 `allowed_mentions`：預設誰都不通知，只放行 `FBWATCH_SUMMON_USER_ID`。
以前沒帶，貼文內文寫 `@everyone` 會真的通知全伺服器。

### 商品標題

商品卡片的標題不在 `story_message` 裡，而在「NT$1,600 · 新北市」那一行的下一個兄弟區塊。
錨點用文字（最深的 NT$ 開頭節點）不用 class，class 每次改版都換。
2026-11-09 對 1183 筆舊資料回填：有價格列的 1022 筆抽到 1021 筆。舊資料重跑：

```bash
FBWATCH_DSN=... go run ./cmd/backfilltitle          # 只統計
FBWATCH_DSN=... go run ./cmd/backfilltitle -write   # 寫入
```

通知會把標題放在內文前面（內文已含標題就不重複），關鍵字比對也涵蓋標題。

## 社團可以分流到不同聊天室

`groups.webhook_env` 填環境變數的**名稱**，值放在 `.env`：

```sql
UPDATE groups SET webhook_env = 'DISCORD_WEBHOOK_URL_B' WHERE id = '<社團 id>';
```

```
DISCORD_WEBHOOK_URL_B=https://discord.com/api/webhooks/...
```

`NULL` 表示用預設的 `DISCORD_WEBHOOK_URL`。告警、熔斷、賣貨便變動**永遠**走預設管道
—— 系統訊息分流只會讓人漏看。

**資料庫只存名稱，不存網址。** 這個專案的憑證一律放 `.env`（`PG_PASSWORD`、
`VNC_PASSWORD`、`MINIO_PASSWORD` 都在那裡），寫進資料庫的話 `dumps/` 裡的
`pg_dump` 檔案就帶著一把可以對那個頻道發文的鑰匙。代價是新增管道要重啟容器；
開關社團仍然不用。

兩個刻意的設計：

**找不到變數時不送，也不退回預設。** 退回預設等於把貼文送到錯誤的聊天室，
而分流的理由本來就是「不要送到那裡」。少送一則下一輪會再試，送錯地方收不回來。

**送不出去的管道整組排除在佇列之外。** 佇列一次取最舊的 20 則，
不排除的話一個設錯 webhook 的社團會用送不出去的貼文把額度塞滿，
其他社團跟著一起停 —— 一個設定錯誤變成全站故障。

排除清單傳進 SQL 時一定要是非 nil 的空切片。`nil` 會變成 SQL 的 `NULL`，
而 `x = ANY(NULL)` 是 `NULL` 不是 `false`，`NOT NULL` 還是 `NULL`，
`WHERE` 就把每一列都濾掉 —— 沒有壞掉的管道時（也就是絕大多數時候）
一則通知都不送，而且完全不報錯。有測試釘著這條。

## 社團可以只通知特定主題

`groups.require_patterns` 填一組詞，只有命中其一的貼文才通知。
`NULL` 或空陣列表示不過濾 —— 設定從缺退回原本的行為，不是把社團靜音。

```sql
UPDATE groups SET require_patterns = ARRAY['顏料','噴槍','抽風'] WHERE id = '...';
```

比對規則與關鍵字提示**共用同一套**（`keyword.Filter`）：全拉丁字加 `\b` 邊界，
其餘用子字串。共用是刻意的 —— 兩邊各寫一次，遲早會在其中一邊發現
「`AK` 為什麼會命中 `Sneaky`」。實測資料裡 `ILIKE '%AK%'` 會吃到 `Sneakers`、`Makeup`
這類完全無關的字，加了邊界之後只剩真正的 AK 牌塗料。

**命中與否的處置不對稱**，這是整個功能最重要的一點：

| 情況 | 行為 |
|---|---|
| 命中 | 馬上送，不等補抓內文 |
| 沒命中，內文已定案 | 標記處理完畢，不送 |
| 沒命中，內文還可能變豐富 | **先留著**，下一輪補到完整內文再重判 |

feed 上的截斷內文可能根本還沒講到關鍵字（有貼文把品項列在第二段），
這時候判死會漏掉真正想要的貼文。漏掉比晚一輪嚴重得多。
「定案」指補抓成功或重試次數用盡（上限 3 次），所以不會無限期卡著。

濾掉的一定要標記處理完畢。不標的話會一直留在佇列裡重判，佔滿 20 則的額度，
最後連該通知的也擠不進來 —— 跟壞掉的 webhook 會造成的是同一種故障。

濾掉的貼文會在日誌留下第一行內容，事後查得出濾掉了什麼。資料庫裡原文都還在：

```sql
SELECT left(COALESCE(body, body_feed), 60) FROM listings
WHERE group_id = '...' AND notified_at IS NOT NULL ORDER BY first_seen DESC;
```

## 同內容去重

同一個賣家把同樣的內容貼到兩個社團，或隔天重貼，只通知一次。實測一個月：

| 類型 | 組數 | 多餘通知 |
|---|---|---|
| 跨社團（中位數相隔 **11 秒**） | 331 | 353 |
| 同社團重貼 | 27 | 51 |

**兩把鍵，回答不同的問題：**

- `feed_key` —— 從第一眼的 feed 文字算，只用來挑「疑似」。
- `content_key` —— 從補抓到的完整內文算，這才是**判準**。

分成兩把是因為 feed 文字是截斷的（平均 53 字，完整內文平均 149 字，
51% 的貼文 feed 版被截斷）。實測有賣家用模板發文，兩則**不同商品**
（兩件不同的工具）的 feed 前綴一模一樣 —— 只憑 feed 判，
會誤擋 18 組 / 45 則真正不同的貼文。

**三種判斷：**

| 情況 | 行為 |
|---|---|
| 完整內文相同 | 擋掉，記進 `duplicate_of` |
| 完整內文不同 | 送 |
| 只有 feed 對上，有一邊內文還沒補到 | **先留著**，下一輪再判 |

延遲只落在**疑似重複的那一則**身上 —— 前一則早就送出去了。成本放在很可能
冗餘的那一份上，不影響第一時間看到東西。兩邊內文都定案卻仍比不出來時必須決斷，
這時候選擇**送出**：寧可多一則，不要吃掉可能不同的貼文。

**三個條件缺一不可：** 同賣家（實測 4 組不同賣家內容相同）、
同通知頻道（不看目的地的話，跨社團去重會讓某個頻道整個收不到）、
對方已經通知過。

**還要一個批次內的記憶體集合。** 跨社團那兩則中位數只差 11 秒，幾乎都落在
同一批 `sendPending` 裡，那時候前一則的 `notified_at` 還沒寫進資料庫 ——
只靠查詢會兩則都送出去。

鍵只正規化空白，標點與 emoji 都算數：只差一個價格數字的貼文是「降價重貼」，
那是值得知道的事，不該被併掉。過短的內容（10 字以下）不產生鍵。

`feed_key` 只在第一次寫入時記錄：賣家編輯貼文、feed 上的相對時間變動，
都會讓後來的 `body_feed` 跟當初不同。

## 來源壞掉要有人知道

2026-10-27 發現一個賣貨便賣場從 10-17 起就抓不到東西，**連續失敗十天**，
每分鐘在日誌裡留一行，沒有任何告警。去看那頁才知道賣家把整個賣場關了。

錯誤被當成雜訊，就等於沒有在監控。三類錯誤分開處理，因為處置不同：

| 狀況 | 怎麼認 | 行為 |
|---|---|---|
| 賣家下架整個賣場 | 頁面含 `0102M1` 或「此賣場已由賣家自行下架」 | 通知一次，**自動停止追蹤** |
| 站台沒反應 | 連不上、超時、HTTP 5xx | 連續 **15** 次才告警（約 30 分鐘） |
| 版型可能變了 | 抓到頁面但解析不出商品、4xx | 連續 **5** 次就告警 |
| 抓取不完整 | 商品數掉四成以上（`ErrIncompleteFetch`） | 連續 **3** 輪就告警 |

截斷類的門檻最嚴，因為它跟另外兩類方向相反：其他失敗是「沒拿到資料」，
重試就好；截斷是「拿到了但不敢採信，主動丟掉」—— 保護機制在這期間把所有
商品變動（包含真實的完售與下架）全部擋在外面。連續擋三輪代表要嘛抓取持續
不完整，要嘛**賣家真的清了四成以上的貨，而保護機制會永遠擋著，自己不會好**。

這條路原本完全沒有告警：`SyncShopItems` 的錯誤走 `return err`，最後只落到
`log.Printf("賣貨便抓取失敗: %v", err)`，就是本檔其他地方批評的那個模式。
而且 `return` 會讓當輪剩下的賣場整個跳過。現在跟其他失敗一樣計數、告警、`continue`。

計數歸零的時機也跟著改了：原本抓取成功就 `fails.ok()`，之後才做同步 ——
截斷永遠到不了門檻，等於這個告警不存在。現在只有**整個賣場處理完全成功**才歸零。

分類是用 sentinel（`ErrShopOffline`、`ErrSiteUnavailable`）加 `errors.Is`，
不是比對錯誤字串 —— 字串會跟著文案改。

**門檻分兩級**是 2026-11-02 的教訓：賣貨便午夜回了一串 503 與超時，
系統照設計在第 5 次叫了，但標題寫「可能是版型變了」。錯誤內容在第二行沒錯，
標題卻把人指向完全錯的方向。這兩件事的處置相反 —— 站台沒反應等就是了，
版型變了要去改程式。標題指錯方向的告警，久了就不會被讀。
10 分鐘的維護不值得叫人起來，30 分鐘才值得。

單次失敗很常見（連線抖動、對方重啟），每次都叫會變成雜訊。成功一次就歸零，
所以恢復之後再壞還會再叫 —— 不然第二次故障會被第一次的旗標蓋掉。
計數本身兩類共用：連續失敗就是連續失敗，中途錯誤類型換了也不該歸零。

賣場下架時頁面照樣回 HTTP 200，只有內文會說，所以訊息代碼與中文兩個都認：
文案可能改，代碼可能換。4xx 則**不**歸成站台類 —— 下架的賣場都回 200，
所以 404 代表網址規則變了，那是該看一眼的事。

### 輪詢紀錄

每個賣場每輪都寫一筆 `poll_runs`（`group_id` 放 `GM…` 編號，`new_items`
借來放變動筆數）。2026-11-02 想回答「午夜是不是每天都掛」才發現賣貨便
這條路從來沒留紀錄，只有 FB 社團有，只能看容器還沒輪替掉的那段日誌。
告警告訴你「現在壞了」，紀錄才回答得出「多久壞一次」。

## 節奏調整

輪詢間隔與每輪補抓上限都可用環境變數調整（見 `.env.example`），
下限保護在 30 秒 —— 間隔太短會讓隨機化失去意義，變成穩定的高頻打點。

**調快的收益有限。** 429 筆有精確時間的貼文，把延遲拆成三段
（比對「找到它的那一輪」與「前一輪」）：

| 區段 | 中位 |
|---|---|
| FB 端——上一輪去看過，它還沒出現 | 5.7 分 |
| 輪詢間隔——看得到了，等我們下一輪 | 1.8 分 |
| 抓到之後到送出通知 | 0.5 分 |

94% 的貼文都有第一段。照實際間隔分組看總延遲：間隔 1.3 分→7.3 分、
2.8 分→8.3 分、7.7 分→11.2 分。**地板在 7 分鐘左右**，所以日間的
30–70 秒已經踩在地板上，再快是純粹浪費請求。

### 夜間視窗的邊界比間隔重要

起點原本是 1 點，設錯了。每小時的貼文量與中位延遲：

| 時 | 貼文數 | 中位延遲 |
|---|---|---|
| 0 | 17 | 7.6 分 |
| 1 | 15 | 12.7 分 |
| 2–5 | 20（四小時合計） | 8.8–12.1 分 |

01 點跟下午一樣熱鬧，卻因為落在夜間視窗第一格多等 5 分鐘；
02–05 點四小時加起來 21 天才 20 則，那裡慢才是對的。
所以夜間起點改成 2 點，日夜間隔本身不動。
`FBWATCH_NIGHT_START` / `FBWATCH_NIGHT_END` 可調，因為這個邊界
取決於社團的作息，換社團就會不一樣。

## 解析壞掉不能把服務弄停機

2026-10-16 的教訓：貼文裡一串十三位數字（看起來是賣貨便商品編號）
被選成價格，超過 PostgreSQL `integer` 上限（約 21 億），寫入連續失敗三次、
冷卻重試仍失敗，**整個 collector 熔斷停機**。熔斷機制本身沒做錯 ——
它把一個永遠不會自己好的錯誤正確地停了下來，問題是那個錯誤不該存在。

三層防護，由外而內：

| 層 | 做法 |
|---|---|
| `collectGroup` | **一則寫入失敗就跳過那一則**，其他照常寫、整輪不算失敗 |

剩下兩層是在那一則之內盡量救回有用的值：

| 層 | 做法 |
|---|---|
| `parse.ExtractPrice` | 整段網址先遮成等長空白；超過 `MaxPlausiblePrice`（100 萬）的數字不列入候選 —— 那是訂單編號、商品 id、手機號碼，不是價格 |
| `store.nullableInt` | 塞不進 `int4` 的值一律寫 NULL |

第二層是重點：解析器永遠會有沒想到的輸入，但一個壞掉的數字不該讓寫入失敗。
寧可那一欄是 NULL —— `body` 與 `raw_html` 都留著、`parser_version` 也在，
解析器改好之後可以回頭重算。

遮蔽網址用的是等長空白而不是刪除，因為評分要看數字前後的文字，
位移一偏上下文判斷就錯位了。

### 第一層才是保命的那層

解析層的兩道擋是在調準度：排掉雜訊候選，讓解析器繼續找下一個，
有機會救回真正的價格。它們一定有漏網的輸入。

真正讓服務活著的是最外層：**一則壞掉只跳過一則**。原本是
`return err`，一篇貼文的一個欄位就能讓整個社團那一輪失敗，
連三輪之後熔斷停機 —— 這才是 10-16 停機的結構性原因，
價格溢位只是那天剛好中獎的輸入。

分界線是「全部都失敗」：那代表資料庫掛了或連線斷了，仍然往上報，
熔斷要接得到真正該停下來的狀況。這條線有測試釘著
（`cmd/collect/collect_test.go`，也是這個套件的第一組測試）。

欄位層級的原則：

| 欄位性質 | 壞掉時 |
|---|---|
| 選填（price、posted_at） | 降級成 NULL，原始資料留著之後重算 |
| 身分（listing id） | 拒絕這一則，但不影響其他則 |

**誠實記一筆**：遮蔽網址在 383 則有真實 NT$ 標籤的賣文上，只改變了 1 則的結果，
命中率 35.2% 前後完全沒動。它擋掉的是「把連結裡的編號當成售價」這種荒謬值，
不是讓解析變準。真要做比價，該用的是 FB 自己的 `nt_tag` 而不是內文解析的 `price`。

## 卡住：既不成功也不失敗的死法

2026-11-09 21:03，主 goroutine 停在一個 CDP 呼叫上 **89 分鐘**，完全沒有告警。
堆疊是這樣：

```
main.main → collectGroup → fetch → browser.Load → WaitForFeed
          → browser.OuterHTML → proto.DOMGetDocument.Call   ← 卡死
```

進程活著、Chrome 活著、CDP 端點還會回應，所以 Docker 不重啟、容器健康檢查
看不出異常。**當時的三道防線全部無效**：

| 機制 | 為什麼沒用 |
|---|---|
| `Load`/`LoadPage` 的 deadline 迴圈 | deadline 檢查寫在 `OuterHTML` 之後。它不回來，迴圈就不前進，deadline 形同不存在 |
| 熔斷器 | 數的是失敗。卡住既不成功也不失敗，不產生任何事件 |
| `checkSilence`（6 小時無新項目告警） | 寫在卡住的那個迴圈裡面，永遠輪不到它執行 |

第三條是重點：**監控卡住的那個東西的看門狗，不能被關在它要監控的東西裡面。**

兩層修法：

**一、每組 CDP 往返都有上限**（`browser.CallTimeout`，20 秒）：導向、拉到前景、
讀 DOM、關分頁、讀頁面資訊 —— 會卡住的不是只有讀 DOM。
20 秒是「慢得不合理」而非「慢」：正常的 DOM 快照是毫秒級。

開分頁（`b.Page`）是唯一的例外。包逾時的話回傳的 page 會繼承一個 20 秒就到期的
context，而 `WaitForFeed` 最長要等 60 秒，會被自己的保護砍掉；要正確處理得把
page 的 context 重新綁回母 context，語意微妙又難驗證 —— 綁錯的話一般輪詢
（約 10 秒）看不出來，只有 60 秒的內文補抓會壞。這個風險交給第二層。

**二、迴圈外的看門狗**（`cmd/collect/watchdog.go`）。跑在自己的 goroutine 上，
每 30 秒檢查一次，超過 5 分鐘沒有進展就告警並以非零碼結束進程。

進展要逐步回報，不是整批：每個社團、**每一則**補抓內文、每個賣場各報到一次。
整批算一次的話，單步最久的環節（補抓內文，每則最多 60 秒載入加 5–20 秒間隔）
會讓上限形同虛設。所以正常的報到間隔上限約 80 秒，5 分鐘是三倍餘裕。

結束而不是試著恢復：卡住的是別人的狀態（Chrome 的某個分頁、某條 CDP 連線），
這支程式沒有能力把它清乾淨。entrypoint 的 `wait -n` 會跟著收工，
compose 的 `restart: unless-stopped` 把整個容器連同 Chrome 一起重來。
**重啟掉幾分鐘的資料，卡住掉幾小時。**

逾時只能擋已知的卡點，看門狗擋所有未知的 —— 所以第二層比第一層重要。

## 熔斷

存在的理由只有一個：**重試迴圈會把軟性封鎖升級成硬封鎖。**

| 情況 | 行為 |
|---|---|
| 導向登入頁或 checkpoint | 立即停止，Discord 告警，不重試 |
| 連續 3 次抓取失敗 | 冷卻 30 分鐘後重試一次，再失敗則停止 |
| 6 小時沒有新項目 | Discord 提醒（解析器可能被改版打壞） |

熔斷後行程不會結束——容器設了 `restart`，結束會被重啟然後再打 FB 一次，
正是熔斷要避免的。改為停止輪詢但保持存活，noVNC 仍可連入重新登入。

## 架構

```
collector ──寫入──> Postgres <──讀取── notifier ──> Discord webhook
(Chrome + go-rod)   (唯一真實來源)
```

collector 只負責取得並寫入原始資料，不做通知、不做分析。爬蟲是最脆弱、
最不該頻繁改動的部分，加功能不該波及它。
